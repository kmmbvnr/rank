# mlRank: дорожная карта от GPU MVP до GPT-2

Обновлено 2026-10-29. Задачи 1–12 выполнены в ограниченном срезе; полный forward и генерация GPT-2 также работают. Ближайшая цель — цельное, читаемое описание GPT-2 вместо ручной сборки GPU-вызовов. Открыты композиция RAM-кода, автоматическое исполнение по частям и размещение больших весов (13a/13b/15). Текущие команды, ограничения и результаты проверок находятся в [README](README.md#implemented-hello-world-subset).

## Цель и границы

**Ближайший пользовательский результат — понятный, работающий GPT-2 на Rank.**
Ученик должен видеть архитектуру в коде, читать и менять вычисления transformer-блока.
Небольшие современные модели порядка 0.5–2B, например Qwen и Gemma, остаются
дальнейшим ориентиром для общности реализации. Сейчас заканчиваем базу и GPT-2;
реализацию новых архитектур в ближайший этап не включаем.

Целевое разделение ответственности:

- Короткая `.ra` открывает веса, подготавливает вход, управляет генерацией и показывает результат.
- Связная `.ram` описывает модель: embedding, attention, MLP, нормализации и выход.
  Общие блоки переиспользуются как функции; файлы разделяются по смыслу, а не по
  GPU-вызовам. Формы промежуточных тензоров выводятся из операций; объявления нужны
  на внешних границах и при неоднозначности, а не после каждого действия.
- Компилятор/runtime разбивает вычисление под ограничения backend, размещает веса,
  передаёт промежуточные состояния и освобождает временные буферы. Пользовательский
  код модели не содержит ручной нарезки матриц и десятков `gpukeep`/`gpufree`.
  Одно описание может исполняться несколькими GPU-графами. План исполнения и
  потребление памяти доступны для просмотра; математические операции модели
  остаются явными в Rank.

Это целевой контракт, а не описание уже реализованного поведения. Точные новые
синтаксические формы и API определяем по целевому коду и аудиту текущего языка.
Существующие многофайловые примеры GPT-2 — проверенные технические стенды и эталоны
для регрессии. Полный forward, генерация, KV-кеш, batched prefill и явное удержание
состояний уже проверены на Mac, Intel `jack.lan` и OnePlus, но ещё требуют ручной
оркестрации. Новый этап должен устранить эту обязанность пользователя.

**1 GiB весов — первая проверяемая цель инфраструктуры, а не потолок языка.**
Размер checkpoint отделён от одновременно занятой GPU-памяти. Веса остаются
файловыми тензорами; при нехватке памяти вычисление исполняется частями в выбранном
бюджете. Текущие 128 MiB — программное ограничение MVP, которое нельзя выдавать за
предел оборудования или достаточную поддержку больших моделей. Проверка 1 GiB
поддерживает цель читаемого GPT-2 и не заменяет её отдельным вручную нарезанным демо.

Для этого пути используем один бэкенд: LiteRT GPU на всех трёх платформах. Рабочая точность арифметики — `.f32`. Текущее `.f16` у ReLU означает округление на границе вызова и не доказывает FP16-вычисления внутри GPU. CoreML, ONNX, NPU и другие форматы точности остаются отдельными направлениями.

Модуль `.ram` хранится вместе с основной программой. На Android пользователь работает с программой, вкладками и вложениями; доступ к обычной файловой системе не является условием запуска. Импорт, экспорт и восстановление программы должны сохранять её модули и будущие бинарные веса.

Сроки определяем после проверки очередного этапа на устройствах. Поддержку операций, fusion, отсутствие копирований и ускорение нельзя выводить только из наличия оператора в формате модели. Размеры тензоров проверяем по контрактам операций и фактическим ограничениям бэкенда; общей обязательной кратности 16/32 не вводим.

## Как принимаем каждый шаг

- Числа и формы сверяем с обычным Rank, а для импортированной модели — также с независимым эталоном. Допуски задаём для конкретной операции и точности. Проверяем отрицательные значения, некратные размеры и граничные случаи.
- Подтверждаем выполнение всего графа на GPU Mac, Intel и OnePlus. На desktop проверяем полную делегацию через API; на Android — по нативным логам. Ошибка или отсутствие GPU не должны незаметно включать CPU fallback.
- Проверяем повторный запуск, изменение источника или весов и соответствующую инвалидацию кеша. Для пользовательского примера проверяем путь Program → RAM → GPU → результат в приложении.
- Корректность, потребление памяти и скорость оцениваем отдельно. Начиная с законченного MLP измеряем холодный запуск, повторный вызов, передачу данных и память на всех трёх устройствах.
- Обновляем существующую документацию и сохраняем законченный шаг отдельным коммитом. Тесты запускаем по затронутому поведению; полный набор проверок не считаем пройденным по результатам профильных тестов.

## Выполненная основа: задачи 1–4

### Задача 1. Поэлементная активация (Hello World)
* **Код `.ram`:**
  ```rank
  use ml
  arg X .f16 shape 1 64
  return X relu
  ```
* **Цель:** Базовая кодогенерация оператора (`Relu` / `mb.relu` / `RELU`), выделение буферов, запуск на чипе, считывание результата в Rank.

### Задача 2. Запекание весов и констант (`option = Default`)
* **Код `.ram`:**
  ```rank
  use ml
  arg X .f32 shape 1 64
  arg Scale .f32 shape 1 64 = array shape 1 64 fill 2.0
  arg Bias  .f32 shape 1 64 = array shape 1 64 fill 0.5
  return (X * Scale) + Bias
  ```
* **Цель:** Разделение runtime-входов (динамические тензоры параметров) и запекаемых весов (Initializers в ONNX, FlatBuffer Buffer в LiteRT, `mb.const` в MIL). Оффлайн-упаковка весов в память модели.

### Задача 3. Аппаратное матричное умножение (GEMM / `linear`)
* **Код `.ram`:**
  ```rank
  use ml
  arg X .f32 shape 1 64
  arg W .f32 shape 64 128 = array shape 64 128 fill 0.5
  return X W linear
  ```
* **Реализованный срез:** `X[M,K] × W[K,N] → [M,N]`, один runtime-вход и запечённые `.f32` веса. LiteRT `FULLY_CONNECTED` на GPU; некратные 16/32 размеры передаются без ручного padding. Формы проверяются до запуска.
* **За пределами среза:** `.f16` матричная арифметика, динамические веса, батчевые матрицы ранга > 2, отдельные AMX/Hexagon/NPU-бэкенды.

### Задача 4. Бродкастинг
* **Код `.ram` (реализован):**
  ```rank
  use ml
  arg BatchScores .f32 shape 1 16 64
  arg Bias .f32 shape 64 = array shape 64 fill 0.5
  return BatchScores + Bias
  ```
* **Реализованный срез:** `+` и `*` совмещают последние оси, как обычная арифметика Rank без модификатора `rank`. Размеры должны совпадать либо один из них равен 1. Формы проверяются до запуска. Статические reshape согласуют формы LiteRT; reshape констант выполняется при компиляции.
* **Проверки:** bias по строкам, одиночные оси, расширение runtime-входа, ранги 1–4, численное сравнение с CPU Rank и выполнение на GPU Mac, Intel и Android.
* **За пределами среза:** явный `rank L R`, скалярные литералы, `.f16` арифметика. У запечённых арифметических констант ранга 4 первая ось должна быть 1; остальные варианты отвергаются из-за ограничения GPU-бэкенда.

## Ближайший MVP: задачи 5–8

### Задача 5. Softmax и простые присваивания

**Реализовано:** `softmax` по последней оси для `.f32` и последовательные присваивания `Name = expression`. Имена связываются с узлами графа; переопределение имени сохраняет ранее построенные зависимости. Неизвестные имена и неподдерживаемые конструкции дают ошибку с местом в `.ram`.

Проверено по 60 GPU-вызовов на Mac, Intel и OnePlus: ранги 1–4, большие положительные и отрицательные значения, равные значения, ось длиной 1, суммы вероятностей, независимость строк, повторное использование и переопределение имени. Максимальная абсолютная ошибка ниже 8e-8. На Android также проверены редактирование модуля, запуск из Program и сохранение после перезагрузки.

**Ограничения:** только обычное `=`; отложенные, составные и индексные присваивания не поддерживаются. Скорость и экономия памяти этим этапом не заявляются.

### Задача 6. Законченный небольшой MLP

**Реализовано:** пример GPU MLP (`mlp.ra` + `classifier.ram`): XOR, два линейных слоя с bias, ReLU и softmax, формы `[4,2] → [4,3] → [4,2]`. Веса аналитические, не обученный checkpoint; их происхождение, уравнения и эталонные значения зафиксированы в [README](README.md#complete-small-mlp).

На Mac, Intel и OnePlus прошли по 42 GPU-вызова: скрытые активации, logits, вероятности, классы, отрицательные/дробные входы, повторные вызовы и замена весов. Максимальная абсолютная ошибка ниже 5.48e-8. Проверены запуск Program → RAM → GPU, сохранение и повторный запуск на Android, round-trip ZIP с исходниками и весами.

Записаны первые измерения холодного и повторного вызова, размера передаваемой модели и памяти процессов. Накладные расходы передачи пока измеряются вместе с сериализацией/планированием, память — снимками, не пиком. Сравнение скорости с CPU и подробное разделение затрат остаются задачей 8. Fusion, экономия памяти и ускорение не заявляются.

**Задачи 7–12 ниже выполнены.** Результаты настоящего GPT-2 и генерации описаны в задачах 13–15. Сравнение Core ML на Mac также закончено.

### Задача 7. Бинарные вложения и жизненный цикл модели

**Реализовано:** MLP использует четыре бинарных `.rwt` вложения. В `arg` вместо массива можно указать имя файла: `arg W1 .f32 shape 2 3 = "w1.rwt"`. Проверяются dtype, форма, точная длина, SHA-256 и конечные значения. На CLI файл находится рядом с модулем; Android и браузер используют вложения программы без системных путей.

Протокол `load → modelId → invoke` загружает модель один раз. Повторный вызов передаёт ID и входной тензор; смена исходника или весов создаёт новый граф. Runtime хранит одну модель, освобождает предыдущую при замене и поддерживает `release`. Устаревший ID возвращает `STALE_MODEL`; клиент восстанавливает модель и повторяет вызов один раз. Обычные ошибки вычисления не повторяются.

Веса сохраняются вместе с программой и отдельными бинарными файлами в ZIP; скомпилированные артефакты не сохраняются. Проверены архивный round-trip, запуск/перезагрузка на Mac и OnePlus, замена весов и перезапуск Android-приложения. Android-хранилище читает большие снимки частями; вложение 2.8 MB прошло сохранение и чтение. Отдельного редактора вложений пока нет: замена пользовательских весов выполняется через ZIP. Процесс загрузки и самостоятельного создания весов пользователем отложен для отдельного обсуждения.

На Mac, Intel и OnePlus прошли по 42 GPU-вызова, максимальная абсолютная ошибка ниже 5.48e-8. Проверены освобождение и устаревшие ID; на desktop — реальный перезапуск helper и замена бинарных весов в уже импортированном модуле. Полный MLP выполняет все 12 узлов на GPU.

FlatBuffer уменьшился с 2072 до 1924 байт: исходная матрица `linear` не сериализуется, если нужна только транспонированная; reshape-константы переиспользуют буфер. Повторный запрос занимает 109 байт на desktop и 94 на Android и не содержит модели. Тензоры пока остаются JSON-массивами; отдельный бинарный транспорт требует измерений задачи 8. Исходные веса ещё декодируются и хранятся в памяти компилятора; уменьшение пиковой памяти не заявляется.

Лимиты не увеличены: 1 048 576 элементов на тензор, 32 MiB исходных констант, 128 узлов. Дополнительно проверяются 32 MiB запроса с учётом base64, 8 MiB бинарных вложений программы и 16 MiB распакованного архива. Лимит констант сам по себе не гарантирует, что модель поместится в транспорт. Подробности и результаты — в [README](README.md#binary-weights-and-model-lifecycle) и [замерах этапа 7](../../benchmarks/baselines/2026-10-27-mlrank-weights.json). Скорость и пиковую память оцениваем в задаче 8; Android-тайминги этого прогона получены при активном экране блокировки и для сравнения скорости не подходят.

### Задача 8. Проверка затрат законченного MVP

**Выполнено:** воспроизводимый полный MLP с двумя линейными слоями, bias, ReLU и softmax на пяти размерах: `[4,2,3,2]`, `[256,2,3,2]`, `[1,64,128,32]`, `[16,64,128,32]`, `[16,128,256,64]` (batch, вход, скрытый слой, выход). На каждом устройстве проведены два прогона: прогрев, 15 чередующихся CPU/GPU-замеров и 15 контрольных GPU-вызовов без профилирования. Все 340 GPU-вызовов на каждом хосте сверены с независимым эталоном; максимальная ошибка ниже 1.38e-7.

Отдельно записаны компиляция, импорт, подготовка native-модели, преобразование/запись входа, вызов runtime, чтение/ожидание и упаковка выхода. Остаток времени моста включает JSON, IPC и планирование; это не чистая скорость передачи. Время вызова runtime нельзя отделять от ожидания при чтении и называть временем GPU-ядра.

**Результат:** на Mac и Intel повторный GPU-вызов быстрее измеренной CPU-программы Rank для всех размеров. На OnePlus маленький XOR находится около границы выигрыша; для одного входа `64 → 128 → 32` CPU стабильно быстрее (9.2–10.7 ms против 13.6–14.9 ms). Батчи выигрывают на GPU: например, `[16,64,128,32]` — 17.5–17.8 ms против 38.5–39.1 ms на CPU. Подготовка новой Android-модели вместе с первым вызовом занимает около 0.3–0.6 s. Это сравнение с текущим CPU Rank в float64, не с оптимизированным BLAS; GPU использует float32.

Сохранены размеры моделей/тензоров и доступные RSS high-water marks. Desktop-пики включают компилятор, CPU-вычисления и стенд. На Android записаны PSS/RSS и наблюдавшийся VmHWM; полный пик с отдельным WebView renderer не измерен. Уменьшение памяти не заявляется, лимиты не повышаются.

**Решение:** использовать батчи там, где это допускает задержка. Для Android сначала исследовать транспорт и работу хоста, если потребуется уменьшать latency: они дороже выполнения графа. Собственные fusion, ядра, arena и новый бинарный транспорт этим набором не обоснованы. Оптимизацию повторного хеширования весов связать с отложенным процессом изменения вложений. Продолжаем к задаче 9 без дополнительных runtime-оптимизаций.

Методика, разброс и ограничения — в [README](README.md#mlp-cost-measurements-stage-8), исходные выборки — в [результатах этапа 8](../../benchmarks/baselines/2026-10-27-mlrank-costs.json). Сценарии находятся в `benchmarks/mlrank/`.

## Путь к transformer-блоку: задачи 9–12

### Задача 9. LayerNorm и GELU — выполнено

Для цели GPT-2 реализовать LayerNorm по последней оси с epsilon, scale и bias, затем нужный вариант GELU. Сверить определения с выбранной эталонной моделью; [конфигурация GPT-2](https://huggingface.co/openai-community/gpt2/blob/main/config.json) задаёт `gelu_new` и `layer_norm_epsilon = 1e-5`.

Проверить постоянные строки, малую дисперсию и численную устойчивость. Нативный оператор или разложение в подграф выбирать по поддержке и результатам на трёх GPU. Не предполагать наличие отдельного LiteRT `LAYER_NORM` или автоматического fusion.

**Результат:** `X layernorm`, `X Epsilon layernorm` и `X gelu_new` реализованы для FP32, ранги 1–4. Scale/bias применяются через `*` и `+`. Отдельные операции и нормализованный MLP с GELU проверены на Mac, Intel и OnePlus; максимальная ошибка меньше 2.9e-7 при atol=rtol=1e-5. Устойчивое разложение использует SUM/division и повторное центрирование остатка; проблема полного MEAN-графа на Metal описана в [результатах](README.md#layernorm-and-gelu-stage-9). RMSNorm остаётся дополнительной операцией для моделей, которым он нужен.

### Задача 10. Структурные операции и несколько входов — выполнено

Добавить доступные из `.ram` статические `reshape`, `transpose`, срезы и concat, затем несколько runtime-входов с проверяемыми типами и формами. Внутренние reshape из задачи 4 ещё не означают поддержку пользовательского reshape.

Расширить `linear` на ведущие измерения и добавить матричное умножение двух вычисленных тензоров с батчами. Это отдельная возможность: текущий `linear` принимает только двумерный вход и запечённую правую матрицу. Проверить несмежные после transpose оси, несовместимые формы и расширение батчей.

**Результат:** reshape, transpose, статические диапазоны и concat, несколько FP32-входов, batched linear и `matmul rank 2 2` реализованы. Проекция QKV, разделение голов и QKᵀ проходят 26 сценариев на Mac, Intel и OnePlus: 78/78/156 вызовов, максимальная ошибка около 1.02e-7. Сверены формы и числа с обычным Rank и независимым эталоном; подтверждена полная GPU-делегация. На Android проверены редактирование RAM, запуск из Program и сохранение после перезагрузки.

Implicit batch broadcasting LiteRT на Metal дал неверный результат на перекрёстных singleton-осях. Компилятор явно расширяет батчи через GPU concat; отсутствие копирований и ускорение не заявляются. Ограничения и воспроизводимые проверки — в [README](README.md#structural-operations-and-multiple-inputs-stage-10) и [результатах](../../benchmarks/baselines/2026-10-27-mlrank-structure.json).

### Сравнение Core ML на Mac — выполнено

Проверены девять нагрузок в двух прогонах, 124 сочетания графа/режима/прогона.
На крупном matmul Core ML быстрее LiteRT: около 0.93 против 1.24 мс в GPU-режимах
и 0.234 против 0.297 мс на CPU. Для маленького QKV LiteRT CPU быстрее Core ML CPU:
0.006 против 0.028–0.031 мс. Core ML назначает маленькие графы CPU даже при
разрешённом GPU; GPU выбран в плане только для крупного matmul.

Стандартный LayerNorm Core ML не прошёл строгий допуск на строках около 1000;
наше устойчивое разложение прошло. Ошибка implicit batch broadcasting LiteRT
воспроизводится на GPU, но не на CPU с тем же FlatBuffer. Это не доказывает
неисправность Metal как API.

**Рекомендация:** для ближайшего MVP сохранить LiteRT и перейти к attention.
Core ML оставить кандидатом на отдельный Apple-бэкенд после сравнения полного
блока. CPU/GPU-политику выбирать явно; текущий GPU-only контракт не менялся.
[Методика и результаты](README.md#core-ml-comparison-on-mac-2026-10-27).

### Задача 11. Маленький attention-блок — выполнено

Собраны Q/K/V-проекция, разделение голов, QKᵀ, масштабирование на 1/√D,
запечённая каузальная маска, softmax, умножение на V, объединение голов и
выходная проекция. Используются существующие операции без нового fused-оператора.
Пример: `demos/mlrank/attention.ra` + `attention.ram`; веса демонстрационные.

Проверено 2026-10-28: 36 вариантов, 108 GPU-вызовов на Mac, 108 на Intel,
216 на OnePlus. Независимый скалярный эталон сравнивает scores, masked scores,
вероятности, контекст, объединённые головы и выход. Контексты 1/3/5, batch 1/2,
голов 1/2, ширина головы 3. Проверены сумма вероятностей, нулевое внимание
к будущим позициям и неизменность предыдущих выходов при изменении последнего токена.
Android UI проверяет компиляцию из RAM, запуск из Program и сохранение исходника.

Веса теперь материализуются обычным интерпретатором Rank при компиляции:
целые литералы (`fill 1`), диапазоны, вычисляемые формы, операции над массивами
и ссылки на предыдущие веса. Результат проверяется по форме и переводится в FP32.
Пользовательский интерфейс загрузки/создания весов по-прежнему отложен.

Сырые результаты: `benchmarks/baselines/2026-10-28-mlrank-attention.json`.
Это проверка корректности короткого фиксированного графа, не производительности
полной модели. Fused attention остаётся вопросом после измерений.

### Задача 12. Маленький transformer-блок — выполнено

Собран фиксированный pre-norm блок: affine LayerNorm → causal attention →
residual → affine LayerNorm → MLP с расширением ×4 и GELU → residual.
Проекции имеют bias, масштаб и смещение LayerNorm нетривиальны.
Пример: `demos/mlrank/transformer.ra` + `transformer.ram`.
Новые операции, циклы и инлайнинг подграфов не потребовались.

Проверено 2026-10-28: 66 вариантов (11 промежуточных выходов, три формы,
исходный и изменённый последний токен). На Mac и Intel — по 198 обычных
GPU-вызовов и 6 дополнительных с измерением памяти; на OnePlus — 396 вызовов.
Максимальная ошибка ниже 5.34e-7 при atol=rtol=1e-5. Разные компоненты последнего
токена изменяются по-разному, чтобы LayerNorm не убирала тестовое изменение.
Проверены вероятности и неизменность предыдущих выходов.

Полный блок занимает 115 узлов, модель — 10–12 KiB. Пиковый RSS нативного
помощника в этом прогоне: 54.8 MiB на Mac и 113.2 MiB на Intel.
На OnePlus измерены PSS/RSS всего приложения во время серии вызовов;
это не память тензоров и не прогноз для GPT-2. Подробности и сырые измерения:
`benchmarks/baselines/2026-10-28-mlrank-transformer.json`.

## Полная модель и генерация: задачи 13–15

### Задача 13. Импорт весов и полный forward GPT-2

**Коррекция 2026-10-28:** целевой путь должен поддерживать наборы весов размером
в гигабайты. Конвертация всего checkpoint в небольшие `.rwt` вложения не является
решением этой задачи. Существующий путь остаётся для маленьких программ и тестов.
На момент этой коррекции полный forward ещё не был реализован; текущий результат описан в 13c.

Проверен полный заголовок Safetensors `openai-community/gpt2`, revision
`607a30d783dfa663caf39e06633721c8d4cfcd7e`: 160 тензоров, 548 090 880 байт
payload (включая сохранённые attention-маски), 37 тензоров превышают текущий
предел 1 048 576 элементов. Embedding `[50257,768]` занимает 154 389 504 байта;
QKV `[768,2304]` и MLP `[768,3072]` также превышают предел одного тензора.
Одно разбиение по transformer-блокам эти ограничения не снимает.
Это аудит метаданных, не проверка размещения или запуска модели.
[Данные и воспроизведение](../../benchmarks/baselines/2026-10-28-mlrank-gpt2-capacity.json).

#### 13a. Хранение и загрузка больших весов — в работе

**Первый срез реализован:** обычный Rank читает индекс Safetensors и отдельные
тензоры с диска блоками до 64 KiB. Проверен sparse-файл больше 2 GiB, включая
доступ за границей 2 GiB, обычные операции и типы чисел. Android получил доступ
к файлам `files/models` отдельно от вложений notebook. Desktop и Android runtime
принимают дескриптор подготовленной LiteRT-модели и проверяют SHA-256 потоково;
небольшой граф с настоящими весами GPT-2 проверен на Mac, Intel и OnePlus.

**Файловый вход `.ram` также реализован:** отложенный F32-тензор проходит через
проверки привязки и передаётся нативному runtime дескриптором, без `number[]` и
JSON с весами. Desktop использует mmap выбранного диапазона; Android — нативное
чтение в буфер, который требует Kotlin API LiteRT. Это runtime-вход, а не запечённая
константа. Неизменённые файловые входы переиспользуют нативный буфер; версия и
размер файла проверяются перед каждым вызовом. Замена модели и release освобождают
эти входы. Файловый runtime-вход теперь допускает до 16 MiB, все входы вместе —
до 64 MiB; пределы вычисляемых тензоров, запечённых констант и числа узлов сохранены.
Нулевое копирование в GPU не заявляется.

Крупная QKV-проекция GPT-2 `[768,2304]` (7,08 MB весов) проверена на Mac, Intel и OnePlus
с разными входами, повторным использованием весов, отклонением устаревшей версии
и повторной загрузкой после release. Пиковая память native-процесса записана;
на OnePlus записаны снимки PSS приложения и проверен запуск из Program после
перезагрузки. Это матричное
умножение без bias, а не законченный attention или полный forward.
Результаты: `benchmarks/baselines/2026-10-28-mlrank-resident-projection.json`.

**Набор и шарды реализованы:** локальный импортёр фиксирует размеры и SHA-256
файлов в индексе `weight_map`; программа закрепляет SHA-256 самого индекса через
`File verify Sha256`. Просмотр метаданных читает только заголовки, выбор тензора
проверяет весь выбранный шард потоково один раз на открытый checkpoint. Повторное
открытие повторяет проверку; закрытие индекса закрывает его шарды. Обычный Rank
и GPU используют те же файловые представления, без массива весов в JS.
На Mac, Intel и OnePlus проверены два настоящих файла весов и отдельный sparse-файл
больше 2 GiB с полной проверкой SHA-256 и GPU-доступом за границей 2 GiB. Записаны
объём JS-чтений и максимальный RSS процессов. Импортёр работает с локальными
файлами; UX загрузки/создания весов и упаковка внешних checkpoint ещё отложены.
Результаты: `benchmarks/baselines/2026-10-28-mlrank-checkpoint.json`.

Это ещё не весь 13a: остаются проверка ограничений больших артефактов LiteRT
и измерения памяти при размещении полных частей модели.
Существующий RAM-компилятор пока строит маленькие графы в JavaScript. Файловый
runtime не означает, что этот компилятор уже поддерживает гигабайтные константы.
[Текущий API и проверки](README.md#file-backed-weights-and-native-models-stage-13a-first-slice).

- Хранить checkpoint отдельным набором файлов на диске. Программа хранит ссылку
  на набор и проверяемую идентичность версии, а не base64 весов в notebook/ZIP.
  На Android файлы находятся в хранилище приложения; системный выбор файла
  может быть источником импорта. Полный UX загрузки/создания весов остаётся
  отдельной задачей, но транспорт должен сразу допускать большие файлы.
- Читать индекс тензоров отдельно от данных: имя, dtype, shape, файл, offset,
  length. Поддержать несколько файлов checkpoint; проверять границы диапазонов
  и целостность потоково. Не разворачивать весь checkpoint в `number[]`.
- Передавать нативному runtime дескриптор модели/весов. Большие данные не проходят
  через JSON, base64, worker messages или URL. Проверить файловую загрузку и
  lifetime файлов на desktop и Android. `mmap` сам по себе не доказывает
  отсутствие копий в драйвере или достаточный объём GPU-памяти.
- Проверить ограничения конкретного LiteRT API и сериализации больших моделей.
  Выбрать файловую сборку ограниченных по размеру частей графа либо поддержанный
  механизм внешних буферов. Не предполагать, что один гигабайтный FlatBuffer
  можно создать текущим JavaScript Builder.

**Приёмка 13a:** файл больше 2 GiB и диапазон за границей 2 GiB корректно
адресуются; чтение и проверка целостности не требуют памяти размером с файл;
ошибки усечения/несовпадения версии диагностируются. На Mac, Intel и OnePlus
одна реальная часть весов проходит путь с диска до GPU и даёт эталонный результат.
Измеряются пиковая память и объём копирований. Большой sparse-файл допустим для
проверки смещений, но не считается доказательством запуска гигабайтной LLM.

#### 13b. Компиляция и размещение по бюджету памяти — в работе

Первый шаг выполнен: несколько явно заданных `.ram` частей остаются в кеше
(до 4 моделей, суммарно 128 МиБ расчётных резервов), повторно используют файловые
веса, вытесняются по LRU и автоматически восстанавливаются при следующем вызове.
Проверено на Mac, Intel и OnePlus; демка `gpt2-parts.ra`, результаты
`benchmarks/baselines/2026-10-28-mlrank-parts.json`. Это не предел физической
GPU-памяти. Активации пока проходят через JS. Автоматическое разбиение,
учёт памяти backend и передача активаций без JS ещё впереди.

Второй шаг выполнен: явная desktop-команда `mlrank-prepare-weight.mjs`
преобразует F16/BF16 в F32 и транспонирует матрицы блоками, сохраняет результат
в проверяемый файловый кеш. Подготовленный файл читается обычным Rank и
передаётся на GPU существующим путём. Проверены реальные веса на трёх GPU,
подготовка 1 GiB файла и смещения за 2 GiB. Встроенной подготовки на телефоне,
автоматического преобразования при вызове пока нет.

Третий шаг выполнен: непрерывные файловые срезы сохраняют дескриптор и идут
на GPU без материализации весов в JS. В обычной программе Rank матрица 32 МиБ
обработана четырьмя частями по 8 МиБ одним GPU-графом; проверены Mac, Intel и
OnePlus, вложенные срезы и смещения за 2 GiB. Демка `file-chunks.ra`, результаты
`benchmarks/baselines/2026-10-28-mlrank-file-chunks.json`. Суммирование частичных
результатов выполняется явно на хосте. Автоматического разбиения и передачи
активаций между GPU-частями без JS пока нет.

Четвёртый шаг выполнен: `mlrank-plan-projection.mjs` создаёт видимую пользователю
программу `X @ W.T`, подбирает число строк по бюджету и ограничениям компилятора,
генерирует отдельный модуль для последнего неполного блока и фиксирует SHA-256
исходника. На трёх GPU проверена матрица 32 МиБ с бюджетом 3 МиБ: 10 полных
частей и остаток, 11 вызовов, результат на 8192 числа. Это планировщик одной
проекции с входом `[1, inputs]`, не произвольного графа. Демка
`planned-projection.ra`, результаты `2026-10-28-mlrank-projection-plan.json`.

Пятый шаг выполнен: планировщик поддерживает `[tokens, inputs]` и собирает
`[tokens, outputs]`, учитывает лимиты входных активаций, полного выхода и выхода
части. На Mac, Intel и OnePlus проверены четыре разных токена, 11 GPU-вызовов
и неполный последний блок; веса 32 МиБ проходят одним чтением для всех токенов.
Демка `planned-batch-projection.ra`, результаты
`2026-10-28-mlrank-batch-projection.json`. Полный forward и embedding lookup
остаются в 13c; это проекция контекста, а не реализация всего transformer.

В графе хранить ссылки на большие константы, а не их JavaScript-массивы.
Преобразование ориентации и dtype выполнять ограниченными буферами с кешированием
файлового результата. Разделить пределы исходного checkpoint, части графа,
активаций и GPU-памяти; не заменять все проверки одним большим числом.
Выбрать части графа по измерениям и ограничениям backend, включая embedding/LM
head и крупные проекции. Один маленький блок уже занимает 115 из 128 узлов.
Определить загрузку, повторное использование и освобождение частей; обмен
промежуточными активациями не должен требовать пересылки весов при каждом вызове.
При нехватке памяти выдавать явную ошибку, сохраняя GPU-only контракт.

#### 13c. Настоящие веса и полный forward — выполнено для четырёх токенов

Первый шаг выполнен: `.i32` runtime-входы и GPU gather по ведущей оси
(`W Tokens`), с проверкой целочисленного типа и границ до GPU. Файловые token
и positional таблицы переиспользуются при смене ID. Проверено на Mac, Intel
и OnePlus; демка `file-embedding.ra`, результаты
`2026-10-28-mlrank-embedding.json`. Таблицы в проверке синтетические; настоящий
checkpoint целиком, полный vocabulary и forward этим первым шагом не проверялись.

Второй шаг выполнен: настоящий блок 0 GPT-2 (ревизия
`607a30d783dfa663caf39e06633721c8d4cfcd7e`) с 12 головами, LayerNorm,
`gelu_new` и обоими residual на контексте из четырёх токенов. Все веса блока
и первые четыре строки token/position таблиц находятся в одном F32 Safetensors
(28,376,064 байта payload). Демка `gpt2-block0.ra` явно вызывает embedding,
attention и MLP как три `.ram`-модуля; разделение сохраняет лимит 128 тензоров.
Между модулями 3072 значения активации проходят через хост. NumPy-эталон,
промежуточные значения и причинность проверены на Mac, Intel и OnePlus;
максимальная абсолютная ошибка выхода блока ≤1.99e-4. Результаты:
`2026-10-28-mlrank-gpt2-block0.json`. Это один блок, не полный forward.

Третий шаг выполнен: все 12 блоков и финальный LayerNorm с обученными scale и bias на контексте
из четырёх токенов. `gpt2-stack.ra` выбирает веса по имени в обычном цикле Rank;
четыре GPU-графа переиспользуются, веса текущего блока заменяют предыдущие.
Файл содержит 148 тензоров и 340,248,576 байт payload; резерв графов —
30,230,544 байта, не фактический предел памяти процесса. Активации проходят через
хост, веса блоков перечитываются на следующем проходе. На каждом из трёх устройств
прошло 248,832 сравнения, причинность проверена после каждого блока, повторный
запуск воспроизводит результат. Ошибка финального hidden state ≤3.58e-4.
Демка OnePlus: **GPT-2 12 blocks**. Результаты:
`2026-10-29-mlrank-gpt2-stack.json`.

Четвёртый шаг выполнен: `gpt2-forward.ra` возвращает logits `[4,50257]`
по полному словарю. В одном F32 файле 148 тензоров, 497,759,232 байта payload.
Token embedding выбирает нужные строки файловыми срезами на хосте и складывает
их с positional rows на GPU. LM head читает ту же `wte.weight` частями:
49 блоков по 1024 строки и хвост 81. Веса не дублируются; весь payload не попадает
в JavaScript. Всего 79 GPU-вызовов за проход; шесть форм графов работают через
существующий LRU на четыре модели, ограничения не увеличены.

На каждом из Mac, Intel и OnePlus прошли 1,445,784 сравнения с NumPy-эталоном,
проверка причинности, повторного прохода и argmax. Максимальная абсолютная
ошибка logits ≤2.09e-4. Нативный peak RSS: примерно 185 MiB на Mac и 181 MiB
на Intel; PSS процесса Android при профилировании — около 300 MiB. Это не полная
память приложения с отдельными JS/WebView-процессами. Демка OnePlus:
**GPT-2 full forward**. Результаты: `2026-10-29-mlrank-gpt2-forward.json`.

**Результат задачи 13:** численный контракт полного forward выполнен на контексте
из четырёх токенов. Произвольные длины контекста, FP16/квантование и оптимизированная
генерация этим не доказаны. Веса блоков/head перечитываются на каждом проходе,
активации и logits идут через хост. Следующая задача — токенизация и генерация
на хосте без KV-кеша (14).

### Задача 14. Генерация на хосте без KV-кеша — MVP на четырёх токенах выполнен

Реализованы `bpeencode`/`bpedecode` в `use text` с явным tokenizer JSON:
GPT-2-compatible byte-level BPE, Unicode и специальные токены. Неподдерживаемые
варианты обработки отклоняются. Путь `gpt2-generate.ra` задаёт prompt и `MaxNew`,
пересчитывает полный forward, выбирает argmax на хосте и декодирует полученные ID.
На Mac, Intel и OnePlus `Hello` продолжен до `Hello, I'm` тремя новыми токенами.

Общий контекст ограничен четырьмя токенами. Prompt должен занимать 1..4 токена,
`MaxNew` — неотрицательное целое. Правый padding заполняется EOS, позиции 0..3;
следующий токен выбирается по последнему настоящему входному токену. Проверено,
что замена padding на нули не меняет его logits. Остановка явная: лимит новых
токенов, заполненный контекст или EOS. Сгенерированный EOS в текст не добавляется;
нет молчаливого обрезания prompt или сдвига контекста.

На каждом устройстве прошли 214 сравнений токенизатора с `tokenizers` 0.22.1 и
301,542 сравнения logits с независимым NumPy-эталоном. Проверены остановки без
GPU-вызовов; desktop также проверяет некорректные параметры и смоделированный
выбор EOS. Демка **GPT-2 generate** установлена на OnePlus и запускается из меню.
Результаты: `2026-10-29-mlrank-gpt2-generation.json`.

**Результат:** минимальная генерация текста работает на всех трёх устройствах.
Это ещё не практический контекст для диалога: каждый новый токен требует полного
forward из 79 GPU-вызовов и повторного чтения весов. Следующий этап — задача 15:
контракты prefill/decode и владение KV-кешем. Увеличение контекста и задержку токена
нужно проверять отдельно; совпадение argmax на всех возможных входах не обещается.

### Задача 15. KV-кеш и ускорение генерации — профиль на четырёх токенах проверен

**Выполнено:** явные `gpukeep`, `gpuread`, `gpufree`; сохранённые F32-буферы
передаются следующему RAM-графу без чтения в JavaScript. Старые снимки не
перезаписываются, выгрузка модели не уничтожает кеш, освобождённые ссылки дают
ошибку. Общий бюджет моделей и состояний — 128 MiB, максимум 64 состояния.

`gpt2-generate-kv.ra` подключает отдельный K/V-кеш ко всем 12 слоям GPT-2.
Prefill обрабатывает токены запроса последовательно; decode добавляет один токен.
Контекст ограничен четырьмя токенами, переполнение останавливает генерацию,
повторный запуск создаёт новые кеши. In-place обновления и кольцевой перезаписи нет.
Проекции и кеши остаются на GPU; активации и логиты ещё возвращаются на хост.

На Metal, Intel и OnePlus сверены по 251 285 логитов с независимым полным forward.
`Hello` + три токена и `Hello,` + два дают `Hello, I'm`; ошибка не выше 3.50e-4.
Проверены остановка, повторный запуск и освобождение состояний. Пиковый учтённый
объём состояний на desktop — 328 704 байта, включая заменяемый буфер и проекцию.

ABBA-замер по два запуска каждого варианта: Metal 0.92–1.00 с с кешем против
1.33–1.65 с без; Intel 9.16–9.39 против 10.21–11.51 с; OnePlus 69.60–71.79
против 79.94–80.00 с. Это время всей программы для трёх новых токенов.
Улучшение включает однотокенный MLP и LM head; это не изолированный замер KV-кеша.
Вызовов GPU стало 300 вместо 237; readback уменьшился в четыре раза.
Веса всё ещё перечитываются между слоями: 1.48 GB за три новых токена.

**Очистка выполнена:** неуспешный вызов освобождает созданные им состояния,
сохраняя кеши прежних успешных ячеек. Предпросмотр владеет своими новыми буферами
и не может освободить заимствованный кеш основной сессии. На Android нативный
владелец закрывается при сбое/замене worker; перезагрузка WebView очищает состояния
страницы. Поздние запросы закрытого владельца отвергаются. Следующий запуск после
сбоя использует новый worker без перезагрузки приложения.

Проверены по 70 ошибок на Metal и Intel, изоляция владельцев и запрос в очереди
на OnePlus, ошибка ячейки, перезапуск и настоящее необработанное исключение внутри
worker через интерфейс. Освобождение следует за текущим native-вызовом; зависший
GPU kernel принудительно не прерывается.
Результаты: [state lifetime baseline](../../benchmarks/baselines/2026-10-29-mlrank-state-lifetime.json).

**Коррекция после профиля OnePlus:** основной расход оказался в повторных
проверках размера/версии checkpoint через WebView: 5 958 запросов и около 42 секунд.
Объединены свежие проверки размера/версии и устранены дублирующие проверки внутри
одного обращения к Safetensors. Проверки изменения файла и родительского индекса
сохранены; кеширования метаданных между обращениями нет. После исправления —
1 199 запросов и 8,3–8,6 с на них; полный профилируемый запуск 45,7–46,4 с вместо
79,6–81,5 с. Число GPU-вызовов (300) и объём весов не изменились.
Результаты: [Android profile](../../benchmarks/baselines/2026-10-29-mlrank-android-profile.json).

**Подготовка весов на Android — проверено:** отдельные таймеры показали 16,2–16,5 с
на поэлементное преобразование байтов в F32 из 19,4–19,7 с подготовки. Блочное
преобразование с сохранением проверки конечности снизило эти интервалы до
2,1–2,6 с и 4,8–5,8 с соответственно. Полный профилируемый запуск — 28,3–32,4 с
вместо 44,6–46,7 с. Объём передаваемых весов и GPU-работа не уменьшились.
Результаты: [weight input profile](../../benchmarks/baselines/2026-10-29-mlrank-android-weight-input.json).

**Профиль 16 токенов — выполнено:** отдельное демо `gpt2-generate-kv16.ra` с
двумя RAM-модулями для кеша `[16,1536]`. Проверены prompt из 7 токенов, 6 шагов
генерации, граница 15→16, остановки и неверные входы. Незаполненные позиции кеша
проверены с различающимися по компонентам значениями. На Mac, Intel и OnePlus
сверены по 502 570 logits с независимым полным forward; состояния освобождаются.
Пиковая полезная нагрузка GPU-состояний на desktop — 1 287 168 байт.
Лимит включает prompt и ответ; динамических форм и скользящего окна пока нет.
Старый профиль 4 сохранён, его эталон и GPU-регрессия не изменились.
Результаты: [context-16 baseline](../../benchmarks/baselines/2026-10-29-mlrank-gpt2-context16.json).

**Пакетный prefill 16 — выполнено:** отдельное демо `gpt2-generate-prefill16.ra`
обрабатывает prompt матрицей `[16,768]`, сохраняет K/V всех слоёв на GPU и
продолжает однотокенным decode. Для prompt из одного токена исходная программа
явно выбирает прежний путь без padding. На Mac, Intel и OnePlus проверены по
603 084 logits, включая отдельный тест заполненных посторонними значениями
строк padding; максимальная ошибка 3.50e-4, состояния освобождаются.

Для семи входных и двух новых токенов: OnePlus 52.8–54.7 → 26.8–26.9 с,
Metal 1.44–1.87 → 0.89–0.91 с, Intel 14.72–15.75 → 6.83–6.92 с.
Это по два запуска варианта в порядке ABBA, без профилирования.
GPU-вызовов 494 → 206, чтение весов 3.03 → 0.99 GB; веса ещё не резидентны.
Readback активаций вырос с 1 022 600 до 1 686 152 байт из-за padded-матриц.
Результаты: [prefill baseline](../../benchmarks/baselines/2026-10-29-mlrank-gpt2-prefill.json).

**Активации между RAM-модулями — выполнено:** отдельное демо
`gpt2-generate-retained16.ra` явно удерживает residual/MLP, decode embedding и
нормализованный hidden через `gpukeep`; каждый временный буфер освобождается
после последнего потребителя. Последняя строка prompt выбирается на GPU.
Старый batched-вариант сохранён для сравнения.

На Mac, Intel и OnePlus сверены по 603 084 logits; ошибка не выросла.
Проверены пять сбоев при живых активациях: очистка происходит до уничтожения
интерпретатора. Для семи входных и двух новых токенов readback уменьшился
с 1 686 152 до 423 560 байт, вызовов стало 207 вместо 206. Учтённые состояния
на desktop занимают в пике 1 425 408 байт вместо 1 327 104; чтение весов
не уменьшилось. Логиты и сборка embedding-матрицы ещё используют хост.
ABBA-замер длинного запроса: OnePlus 26.34–26.64 → 19.98–20.48 с,
Metal 0.85–1.19 → 0.68–0.69 с, Intel 6.82–7.70 → 5.14–5.29 с.
Для короткого запроса на Metal диапазоны перекрываются.
Результаты: [retained activations baseline](../../benchmarks/baselines/2026-10-29-mlrank-gpt2-retained.json).

**Явное удержание подмножества весов — реализовано:** отдельный вариант
`gpt2-generate-pinned16.ra` закрепляет 12 выходных проекций attention (27 MiB)
существующими `gpukeep`/`gpufree`, когда возможны хотя бы два шага генерации.
Указанный в программе бюджет весов 32 MiB не меняет общий предел runtime
128 MiB. После pin вес — неизменяемый снимок; новый запуск заново проверяет
checkpoint. При единственном возможном шаге используется прежний файловый путь.

Для двух выходных токенов чтение весов уменьшается с 989 276 160 до
960 964 608 байт; для шести — с 2 967 717 888 до 2 826 160 128 байт.
Это 3–5% объёма, а не решение повторной загрузки всей модели. Добавляются
12 GPU-вызовов, нормальный пик состояний desktop — 29 736 960 байт.
Основным демо остаётся вариант с удерживаемыми активациями: небольшой закреплённый
набор не объявляется общим ускорением. На OnePlus два токена заняли около 20 с
в обоих вариантах; шесть — 47.18–49.03 с без pin и 45.91–47.01 с с pin.
На трёх устройствах проверены 603 084 logits, ошибки при живых весах и отказ
при реальном заполнении native-бюджета; после ошибок состояния освобождаются.
Результаты: [pinned weights baseline](../../benchmarks/baselines/2026-10-29-mlrank-gpt2-pinned.json).

## Следующий этап: цельный код GPT-2 и исполнение больших вычислений

Договорённости 2026-10-29 заменяют следующий шаг «закрепить ещё несколько матриц».
Ручные варианты остаются эталонами. Дополнительный фиксированный набор весов сам
по себе не считается продвижением к пользовательскому контракту выше.

1. **Начать с желаемого кода GPT-2.** Выразить один transformer-блок и его
   повторное применение средствами Rank с минимальной обвязкой. Сопоставить его
   с текущими возможностями `.ram`: композиция функций, передача весов, вывод форм
   и повторение блоков. По этому коду выбрать первый недостающий общий механизм
   компилятора и реализовать его с исполняемым примером и тестами. Проектные фрагменты
   до реализации явно отмечать как предложения; одного красивого псевдокода для
   приёмки недостаточно.
2. **Передать разбиение и время жизни runtime.** Цельное описание автоматически
   превращается в исполняемые части, сохраняющие промежуточные тензоры без
   обязательного возврата на хост. План учитывает веса, активации, KV-кеш и
   ограничения конкретного backend; освобождает ресурсы при завершении и ошибках.
   Разбиение не требует отдельных пользовательских `.ram` и повторения деклараций
   форм на каждой внутренней границе. Бюджет и фактические передачи наблюдаемы.
3. **Проверить основу на 1 GiB и завершить перенос GPT-2.** Выполнить связное
   матричное вычисление с не менее чем 1 GiB реально используемого содержимого весов
   на Mac, Intel и OnePlus. Файловый ввод не разворачивает весь набор в JS; выбранный
   бюджет ограничивает размещение, результат сверяется с независимым эталоном.
   Измерить память, чтения/передачи, холодное и повторное выполнение; проверить
   изменение файла, недостаток памяти и очистку. Sparse-файл, чтение заголовка или
   использование лишь небольшого диапазона не закрывают эту приёмку. Для проверки
   базы не требуется добавлять новую большую языковую модель.

**Приёмка пользовательского результата:** короткая `.ra` и читаемая реализация
GPT-2 с переиспользуемым блоком, выводом промежуточных форм и без ручного управления
GPU-частями. Один и тот же исходный код работает на трёх устройствах; численная
корректность, причинность, остановки генерации и очистка сохраняются. Сравниваем
затраты с существующими ручными реализациями; автоматизация сама по себе не
доказывает ускорение.

Современные небольшие модели реализуем после этой базы. Расширяемые операции,
формы и работа с весами не должны быть зашиты под GPT-2. Поддержку компактных
форматов весов, большего контекста и конкретных отличий Qwen/Gemma проверяем
отдельными последующими этапами; это ещё не реализованные возможности.
Результаты текущей генерации: [GPT-2 KV baseline](../../benchmarks/baselines/2026-10-29-mlrank-gpt2-kv.json).

## Отдельные направления после MVP

Эти возможности не являются зависимостями запуска небольшого MLP или первого transformer-блока:

- Conv2D, pooling и модели изображений.
- RMSNorm и другие операции под конкретные модели.
- Явные модификаторы `rank L R` и `axis`, расширение поддерживаемого подмножества Rank.
- CoreML/ANE, ONNX и другие GPU/NPU-бэкенды с отдельной проверкой доступности на устройствах.
- FP16/BF16, INT8 и другие форматы, калибровка и оценка качества.
- Собственные fusion и планирование памяти по данным профилирования.
- Перечислимые формы и выбор профиля; общий пул весов и стоимость подготовки проверяются отдельно для каждого runtime.
- Обучение и визуализация: [Training Environment](TRAINING_ENVIRONMENT.md). Apple-специфичные исследования: [CoreML on iOS](IOS_COREML.md).

Предложения в связанных документах описывают более широкий дизайн. Порядок работы и границы ближайшего MVP определяет этот roadmap; новые аппаратные гарантии требуют отдельной проверки.
