# Parallel tensor workers: experiment results

Recorded 2026-09-12. Runtime baseline: `ada5edb`; experiment commit: `ffee766`
on `experiment/tensor-workers`. The experiment remains separate from main.
Raw timing files are retained with this wiki; their `commit` field identifies
the runtime baseline, since the benchmark was recorded before its own commit.

This is an opt-in Node.js experiment, not automatic parallel execution in Rank.
It uses the unchanged interpreter and standard library from this checkout. A
persistent pool runs explicit pure operations over independent input partitions.
The language, synchronous interpreter API, and default execution stay unchanged.

## Run

Run from the experiment checkout (`/private/tmp/rank-tensor-workers` in the
original session), or a worktree at commit `ffee766`:

```sh
npm run build
node --test benchmarks/tensor-workers/test.mjs
node benchmarks/tensor-workers/bench.mjs > workers.json
```

`SAMPLES=9` changes the measured repetitions; `ONLY=multiply` selects one workload.
The default uses three warmups and five alternating measured repetitions per case.
Worker startup is recorded separately. Node version, CPU, base commit and all raw
samples are in the JSON. Run on an otherwise idle machine. These are Node/Mac
measurements, not Android, browser or energy measurements.

## What is measured

- `total`: exact BigInt `A sum`. Parts are summed in workers, then their integer
  results are combined. Real-valued sums are rejected: regrouping their additions
  would change Rank's result. Integers are not narrowed to fixed-width storage.
- `transform`: Rank `(A * A + A * 2.0 + 1.0) copy`, returning all elements.
- `multiply`: Rank `(A B matmul) copy`, partitioned by output rows. Every worker
  receives the entire right matrix. Dot-product accumulation order is unchanged.
- `windows`: Euler 8's width-13 window/product/max pipeline. Each partition owns
  a disjoint range of output windows and reads twelve extra input elements.
- `fused`: a handwritten single-pass JS control for the transform formula. This
  is NOT generated by the current Rank compiler. It indicates whether improving
  local fusion can be more effective than distributing today's runtime overhead.

Inputs use ordinary Rank arrays. There are no shared buffers, transferable
numeric buffers, or hidden BigInt-to-Number conversions. The prototype deliberately
measures the cost of copying the representation currently used by Rank.

`local` runs in the calling thread. `roundtrip` includes partitioning, slicing,
input structured cloning, message delivery, actual Rank computation, output cloning,
and concatenation/reduction. It excludes pool startup, parsing and fixture creation.
Both local and worker array results are fully forced and copied to plain envelopes
before returning, so lazy construction is never mistaken for completed computation.
The local case also pays the envelope copy for a symmetric materialization boundary.

`resident` uploads a partition once and records that cost as `loadMs`. Timed calls
reuse it but still send the complete result back and assemble it. This measures
repeated immutable-input operations, NOT an implemented distributed ML pipeline:
changed inputs would require another upload. Each resident case has its own nearby
`local-control-N` timing to expose warmup or GC drift. Upload and pool startup must
be amortized before claiming a benefit for an application.

All results are checked against independent JS oracles outside the timer, including
shape and every output element. Tests cover uneven partitions, fewer rows than
workers, a maximum window crossing a partition boundary, large exact integers,
rejected floating sums, and a worker-side dimension error. Only the explicitly
listed, valid pure numeric workloads are supported. General error ordering, mutable
aliases, effectful callbacks, lazy input serialization, cancellation, arbitrary axes,
and transparent integration into synchronous execution are outside this prototype.

## Integration implications

A future scheduler should see a typed, pure operation plan and its materialization
boundary. It should first fuse local work, then decide whether the resulting kernel
has enough computation per transferred byte to justify distribution. Splitting
individual cheap expressions is a poor default. Keeping intermediate arrays in
workers could help whole pipelines, but requires ownership and residency tracking.

The prototype is asynchronous at the host boundary (`await pool.run(...)`). A
browser implementation needs Web Workers and a way for the Rank execution driver
to suspend/resume at these boundaries. It cannot simply return a Promise from an
existing synchronous numeric builtin. Workers are threads, not pinned CPU cores.

ML matrix multiplication and independent per-row computations are candidates.
PCA/gradient-descent examples contain such operations, but this benchmark does not
measure those whole programs or parallelize their dependencies. Stick Game's
state recurrence is not made independent by this approach. Small one-shot Euler
inputs are unlikely to repay creating a fresh pool.

## Results: Apple M5, Node 24.15.0

Raw data: [first run](../../benchmarks/baselines/2026-09-12-tensor-workers.json)
and [repeat](../../benchmarks/baselines/2026-09-12-tensor-workers-repeat.json).
The second also includes
the handwritten fused control. Four-worker startup took 164.67 and 165.58 ms.
These times exclude pool startup but include full input/output transport:

| Operation / input | Local, ms | 2 workers, ms | 4 workers, ms |
| --- | ---: | ---: | ---: |
| Integer sum, 1M | 3.17 | 19.60 | 16.01 |
| Rank polynomial, 10K | 1.52 | 0.98 | 0.68 |
| Rank polynomial, 1M | 252.13 | 154.69 | 91.71 |
| Matrix multiply, 64 x 64 | 3.00 | 2.45 | 1.95 |
| Matrix multiply, 128 x 128 | 22.80 | 16.92 | 10.18 |
| Matrix multiply, 256 x 256 | 183.55 | 130.05 | 73.33 |
| Width-13 windows, 1K | 1.91 | 1.03 | 0.80 |
| Width-13 windows, 100K | 189.99 | 96.41 | 57.83 |
| Handwritten fused polynomial, 1M | 1.00 | 64.33 | 51.26 |

For the repeated heavy workloads, the first run gives the same direction: matrix
128 x 128 is 22.05 -> 10.09 ms on four workers; windows 100K is 183.15 -> 58.35 ms;
Rank polynomial 1M is 258.89 -> 95.53 ms. The 16 x 16 matrix timings change within
one run as JIT warms (local 0.29 -> 0.09 ms), so do not use them to select a cutoff.
64 x 64 is a plausible experiment threshold for matmul; 128 x 128 shows a stronger
benefit. These are workload/machine-specific observations, not dispatch constants.

Resident integer sum at 1M takes 1.16 ms on four workers against its local control
of 3.24 ms, but initial upload costs 14.74 ms. Roughly eight repetitions are needed
to amortize that upload alone; a new pool needs roughly 87 including startup.
At 100K the benefit is smaller (0.32 -> 0.18 ms). Returning a full cheaply computed
array remains expensive even with resident inputs: fused 1M takes 46.15 ms.

The most actionable result is the local fused control: 1 ms versus approximately
252 ms through the current Rank expression path. Parallelizing that path improves
it, but removing its per-element overhead could improve it much more. The JS
control omits generic Rank dispatch/type guards and is a target, not a promised
compiler speedup. Its arithmetic order and checked outputs match this fixture.

Recommended next step: improve fusion and dense numeric kernels first; retain this
experiment as evidence for a persistent, opt-in scheduler for expensive independent
operations. Do not enable automatic workers for sum or every array expression.
Mobile crossover, browser startup/transport, peak memory and energy remain unmeasured.

The implementation follow-up is the [fusion improvement plan](tensor-fusion-plan.md).
The experiment passed 977 TypeScript tests and its worker-specific correctness
checks. It did not benchmark the full demo suite or claim whole-program speedups.

## Recheck after local fusion

The [completed fusion stages and worker recheck](fusion-results.md) show that
local fusion reverses the worker advantage for the polynomial map. Heavy matrix
and window calculations can still benefit from a warm pool.
